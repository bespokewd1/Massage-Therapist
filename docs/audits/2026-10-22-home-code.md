# Homepage source audit, 22 October 2026

Audit only. No application source, configuration, or dependency changes were made. This note inspects the current source and existing `dist/` output. The parent audit owns the live Lighthouse measurements. No browser MCP connection was available in this child session.

The supplied mobile run scored 96 with FCP 1.8 s, LCP 2.4 s, TBT 80 ms, CLS 0, and Speed Index 3.1 s. Its five render-blocking CSS requests total 17.9 KiB with an estimated 590 ms saving. Treat that estimate as run-specific, not a promise that a CSS change will save 590 ms. The parent reported a fresh live run where the CSS insight estimated 0 ms.

## Smallest safe candidates

1. **Remove the homepage's unused image preload first.** [index.astro:22](../../src/pages/index.astro#L22), [32](../../src/pages/index.astro#L32), and [86](../../src/pages/index.astro#L86) optimize `landing.jpg` and pass it to [BaseLayout.astro:56](../../src/layouts/BaseLayout.astro#L56). Existing `dist/index.html` requests `/_astro/landing.D_wYLIJw_ZA4HG5.webp`, 112,886 bytes, only in its preload. Nothing on that page displays that URL. The real hero is the CSS background at [index.astro:692](../../src/pages/index.astro#L692), using `hero-img_mobile.webp` or `hero-img.avif`. Keep the responsive hero preloads at [index.astro:88](../../src/pages/index.astro#L88). The mobile hero file is only 9,450 bytes. Removing this one home prop and its now-unused imports avoids about 110 KiB of cold-load competition without changing visible behavior. Do not remove the shared layout preload capability from other pages without checking them separately.

2. **Test CSS inlining, but compare it rather than adopting it blindly.** Astro 5.4.2 is installed. `build.inlineStylesheets: 'always'` is a supported, small configuration experiment. It removes the five linked CSS request dependencies, but embeds 101,452 raw CSS bytes into this HTML and prevents shared external CSS cache reuse between pages. The HTML is already 233,464 raw bytes. Smaller request count does not guarantee a faster page. Compare at least three cold mobile runs, then test repeat visits and internal navigation. Do not change all stylesheets to `media="print"` or defer the hero/navigation styles. That risks unstyled content, delayed LCP, theme flashes, and layout shifts.

3. **If the live trace confirms text LCP, test only its font preload.** The parent identified the hero H1 and Open Sans 500 as current LCP. The H1 gets weight 500 through `.cs-title` in [root.less:84](../../src/styles/root.less#L84). Its local face and `font-display: swap` are already declared in [root.less:198](../../src/styles/root.less#L198). A targeted preload for `/assets/fonts/open-sans-v40-latin-500.woff2` is more defensible than preloading every declared weight. It adds early network competition, so compare it separately from CSS inlining. Do not replace fonts or remove weights merely because a declaration exists.

This is a modest byte cleanup, not a verified 590 ms saving.

## Scripts and forced reflow

### Keep ClientRouter unless its behavior is replaced

[BaseLayout.astro:27](../../src/layouts/BaseLayout.astro#L27) mounts `ClientRouter`. The supplied trace assigns it 34 ms of forced reflow and leaves 14 ms unattributed. Neither number proves that removing the router is the best way to improve LCP.

The router owns initial and subsequent `astro:page-load` events. Both [ScrollToTop.astro:34](../../src/components/ScrollToTop.astro#L34) and [StickyButton.astro:87](../../src/components/StickyButton.astro#L87) initialize only on that event. Both controls start hidden. Removing the router alone leaves them hidden indefinitely. [gallery.astro:149](../../src/pages/gallery.astro#L149) also depends on that lifecycle. Blog listing cards use `transition:name`, and theme/menu logic uses swap events. A full-page-navigation conversion is possible, but it needs replacement initializers and a route-wide interaction check. It is not a one-line safe optimization.

### Navigation and booking are not startup priorities

[nav.js](../../src/js/nav.js) uses document-level delegated listeners. It changes classes/ARIA and resets menus on router events; it contains no layout geometry reads. Do not replace this with per-page listeners just to chase an unattributed reflow.

The [booking dialog at Header.astro:234](../../src/components/Header.astro#L234) opens through native `showModal()` only after a click. It does not embed MassageBook on home. The third-party booking iframe lives on [booking.astro:63](../../src/pages/booking.astro#L63), not home. Keep the dialog's keyboard handling, focus behavior, and menu/dialog interaction when changing navigation. The supplied inline-call entries show 0 ms, so they are not useful first targets.

### Marquee has one measurable read and a lifecycle issue

[Header.astro:1109-1160](../../src/components/Header.astro#L1109) measures the first chunk with `getBoundingClientRect()` after `document.fonts.ready`, then writes `--chunk-width`. This can flush layout, but the supplied trace does not establish a worthwhile saving from removing this particular read.

The script initializes on DOMContentLoaded, not `astro:page-load`. Astro's bundled module runs once, so after a client-side swap the new header does not receive `--chunk-width`; the old resize listener and mutation observer still reference the detached header. This is a source-confirmed lifecycle risk, not a measured startup regression.

A focused repair can initialize on page load and disconnect observers/listeners before swaps. That preserves the current animation but still needs one width measurement. A CSS-only variant can avoid measurement by using a max-content track with exactly two equal-width copies and translating it by `-50%`. That requires consistent gap/padding and matching breakpoints. The current animation applies through 1024 px while `lg:hidden` hides the duplicate at 1024 px. Keep desktop static, respect reduced motion, and test the seam before replacing it.

### Theme must remain early

[ThemeInit.astro](../../src/components/ThemeInit.astro) intentionally runs inline at body start and reruns on swaps. [theme.js:18-27](../../src/js/theme.js#L18) writes the body class and reads `getComputedStyle(document.body)` to update theme-color. The initial call, DOMContentLoaded, and page-load hooks repeat `apply()`, but they preserve the correct saved/system theme before paint and sync the toggle after parsing. A style read is not proof of a layout reflow. Do not delay theme setup to idle for a score tweak. If a new trace attributes material work here, split early class application from later metadata/control synchronization without duplicating theme color constants.

### Scroll controls already avoid scroll-handler work

Back-to-top and sticky booking use `IntersectionObserver`, disconnect before swaps, and initialize against the new page. Sticky booking uses the observer entry's supplied rectangle instead of calling `getBoundingClientRect()` repeatedly. There is no continuous scroll listener to remove. Keep these unchanged unless testing reveals a concrete issue.

## Low-value cleanup and validation

[BaseLayout.astro:88-99](../../src/layouts/BaseLayout.astro#L88) registers a load handler that only flips stylesheet links already marked `media="print"`. None of the five built links has that media. The handler currently makes no stylesheet asynchronous. It can be deleted as dead cleanup, but its expected score impact is negligible.

Validate one change at a time against the same mobile Lighthouse settings. Check saved light/dark modes, system theme, mobile menu and Escape, native booking dialog and focus return, homepage-to-other-route-to-home navigation, marquee after swaps, reduced motion, sticky booking visibility, and footer back-to-top. Keep CLS at its current near-zero level. No audit-only recommendation guarantees a stable score of 100.
